## 3. RLS-сценарии (`rls_isolation_test.sql`)

Самопроверяющийся скрипт: любая непройденная проверка бросает исключение,
поэтому ненулевой код возврата psql = провал.

1. Участник видит ровно свою организацию.
2. Кросс-тенантное чтение возвращает ноль строк для всех tenant-таблиц.
3. Бесплатный entitlement `job_tracker` создаётся вместе с организацией (§13.1).
4. Прямой INSERT в `organizations` запрещён — только через RPC.
5. Чужую организацию нельзя обновить.
6. `is_member_of` для чужой организации — false.
7. Staff не видит подписки, но видит entitlements и свою организацию (§11.3).
8. `audit_logs` неизменяемы даже для владельца таблицы.
9. Работа и клиент создаются, журнал пишется автоматически с верным актором;
   смена статуса, soft delete и восстановление дают свои события;
   `phone_digits` генерируется и находит номер, записанный иначе.
10. Владелец B не видит данных A и видит свои; кросс-тенантные INSERT/UPDATE отклонены.
11. Журнал нельзя ни подделать, ни изменить, ни удалить.
12. Staff работает с Job Tracker своей организации и не видит чужую.
12b. CSV-импорт: атомарность, сопоставление клиента по телефону в другом формате,
    события `job.imported` вместо `job.created`, транзакционно-локальный контекст
    не протекает за пределы импорта, запись в audit log, отказ при кросс-тенантном
    вызове и при значении вне реестра (ни одной строки не остаётся).
13. Организация удаляется при наличии работ; история активности и аудита переживает удаление.
14. Anon видит ноль организаций, работ, клиентов и записей журнала.
15. Матрица грантов Data API совпадает с матрицей политик: у `anon` нет ни одного
    табличного гранта (15a), у `authenticated` нет глагола без политики (15b),
    и нет политики без гранта (15c). Проверка читает `information_schema`, а не
    результат запроса: при forced RLS лишний грант выглядит как пустая выборка и
    иначе не ловится.

## 4. Сквозной сценарий Этапа 2 (§37.3, сценарий A)

Проверяется перед каждым merge — в браузере против реального Supabase и
затем на развёрнутом preview.

1. Вход в кабинет, создание организации (если её нет).
2. Пустое состояние списка работ.
3. Создание работы: клиент, телефон, услуга, статус, источник, расписание, суммы.
   **Критерий §13.11: меньше минуты.**
4. Карточка работы: клиент, деньги, маржа после материалов, расписание в
   таймзоне организации, журнал с событием создания.
5. Валидация: сумма «abc» даёт понятную ошибку у поля, а не 500.
6. Смена статуса с карточки; в журнале появляется переход «из → в».
7. Поиск по телефону клиента, записанному в другом формате; поиск без совпадений
   даёт отфильтрованное пустое состояние.
8. Представления §13.7: работа видна в «Scheduled» и не видна в «Lost».
9. Мобильный экран (390 px): широкой таблицы нет, карточка показывает клиента и статус.
10. Испанская локаль: список и карточка на испанском.
11. Дашборд: счётчики перестали быть прочерками и ведут в нужные представления.
12. Soft delete: работа исчезает из списка, доступна под фильтром «Deleted»,
    восстанавливается; журнал содержит удаление и восстановление.
13. CSV-импорт: файл → сопоставление колонок → preview с дубликатами → подтверждение;
    работы появляются в списке, клиенты сопоставлены, а не задвоены.
14. CSV-экспорт открывается в таблице, колонки совпадают с Jobs-табом §14.7.

### Ограничение окружения

Браузер в сборочном контейнере не имеет исходящего HTTPS, поэтому клиентская
форма входа (она обращается к Supabase напрямую из браузера) в нём не работает.
Сквозной прогон выполняется так: сессия берётся через auth API, кладётся в
cookie `@supabase/ssr`, дальше всё идёт обычным путём — серверные компоненты,
server actions, живая база. Развёрнутый preview дополнительно проверяется
HTTP-запросами с той же сессией.

## 4a. E2E в CI

Job `e2e` поднимает на раннере локальный стек Supabase (`supabase start`:
Postgres + API + auth), применяет к нему миграции из репозитория, собирает
приложение и гоняет Playwright. Секретов по-прежнему нет: ключи локального
стека — фиксированные dev-значения, которые печатает `supabase status`, и
берутся оттуда, а не из GitHub Secrets.

Что покрывают спеки:

| Файл | Сценарий |
|---|---|
| `job-tracker.spec.ts` | Регистрация → onboarding → создание работы → смена статуса, с проверкой таймзоны, сумм и записи в журнал; поиск по телефону в другом формате и отфильтрованное пустое состояние; массовая смена статуса; soft delete и восстановление; понятная ошибка валидации вместо тишины |
| `mobile.spec.ts` | Viewport Pixel 7: широкой таблицы нет, карточка показывает клиента/работу/статус/сумму, нет горизонтального переполнения, тап открывает работу; испанская локаль на телефоне |

Оба макета §13.9 присутствуют в DOM одновременно (один скрыт CSS'ом), поэтому
спеки работают только с видимым: `input[name="job_ids"]:visible`.

## 5. Ручные проверки перед merge (§39)

- [ ] English UI и Spanish UI на месте, ключи не разъехались (typecheck + `i18n-parity`).
- [ ] loading / empty / error / not-found состояния видны глазами.
- [ ] Мобильный экран проверен на 390 px.
- [ ] Клавиатурная навигация: у полей есть подписи, ошибки помечены `role="alert"`,
      цвет не единственный носитель смысла (§8.3).
- [ ] Preview Deployment открыт и ключевой сценарий пройден.
- [ ] В диффе нет секретов.
- [ ] Миграция применена к живой базе и проверена `get_advisors`.

## 5a. Перед запуском

Проверки, привязанные к домену и живым ключам, вынесены в
`docs/HANDYALLIANCE_LAUNCH_CHECKLIST.md` — их нельзя пройти на
`*.vercel.app`, а часть (проверка Google consent screen, свой SMTP) требует
недель, а не минут, и начинается заранее.

Отдельно оттуда, потому что это не «настройка на потом», а **блокер пилота**:
встроенный мейлер Supabase отдаёт единицы писем в час, и тест регистрации
2026-08-04 упёрся в `over_email_send_rate_limit`. До первых живых
пользователей нужен свой SMTP через Resend.
