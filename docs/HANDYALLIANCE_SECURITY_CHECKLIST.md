# HandyAlliance — Security checklist

Статус: живой документ. Отражает состояние после Этапов 1–2.
Основание: `docs/MASTER_SPEC.md` §26, §33, §39.

## 1. Границы доверия

| Уровень | Клиент | Когда допустим |
|---|---|---|
| Browser | anon key | Всегда; RLS применяется |
| Server (session) | anon key + cookies пользователя | Весь кабинет; RLS применяется |
| Server (elevated) | service role | Только webhooks / admin / фоновые задачи. Origin выводится из server-owned `SUPABASE_PROJECT_REF`, а не из публичного URL (`src/lib/supabase/target.ts`); ref'ы проектов BizMetria запрещены жёстко |

Весь Job Tracker работает на session-клиенте: ни один пользовательский путь
не поднимается до service role.

## 2. Мультитенантность (§26.1)

- [x] RLS `enable` **и** `force` на каждой tenant-таблице; реестр-цикл в миграциях
      не даёт забыть новую таблицу.
- [x] Каждая политика идёт через `app_private.is_member_of(organization_id)` /
      `is_org_owner(...)` — security definer с пиненым `search_path`.
- [x] Организация в server actions выводится из сессии, а не из поля формы.
- [x] Нет политики = запрет: `webhook_events` доступна только service role.
- [x] Автотесты межорганизационной изоляции гоняются в CI на каждом PR.

### 2a. Гранты Data API — второй слой, а не комментарий

RLS фильтрует строки; гранты решают, доходит ли роль до таблицы вообще. Слои
обязаны падать независимо, иначе слой один.

- [x] `anon` не имеет **ни одного** табличного гранта в `public`: все политики
      схемы — `to authenticated`, поэтому анонимный запрос должен упираться в
      отсутствие доступа, а не в пустую выборку.
- [x] `authenticated` получает ровно те глаголы, под которые есть политика.
      DELETE — только `organization_members`; удаление сущностей это `deleted_at`.
- [x] Проверка 15 в `rls_isolation_test.sql` читает сами гранты и падает в обе
      стороны: грант без политики (15a/15b) и политика без гранта (15c). Оба
      негативных контроля прогнаны.

**Почему это отдельный пункт.** Проект создан, когда Supabase ещё авто-раскрывал
новые таблицы, и его default ACL выдавал `anon` и `authenticated`
`arwdDxtm` — включая DELETE и **TRUNCATE** — на каждую таблицу, существующую и
будущую, в том числе на `webhook_events`. Миграция `20260804000800` выдавала
узкий набор поверх широкого, то есть не меняла ничего: на живой базе до и после
неё у `anon` было 98 табличных грантов. TRUNCATE не подчиняется RLS вообще —
ни одна политика его не остановит; недоступен он был только потому, что
PostgREST такого глагола не умеет, а это свойство прослойки, а не гранта.
`20260804000900` снимает default ACL и уже выданное, затем возвращает нужный
набор: после неё у `anon` 0 грантов, новая таблица наследует `NONE`.

## 3. Данные Job Tracker (Этап 2)

- [x] `customers` / `jobs`: SELECT/INSERT/UPDATE для активных участников организации;
      **DELETE-политик нет ни у кого** — удаление это `deleted_at` (§14.12).
- [x] `job_activities`: только SELECT. Записи делают триггеры `SECURITY DEFINER`,
      поэтому журнал нельзя ни подделать, ни отредактировать с клиента;
      триггер неизменяемости блокирует UPDATE/DELETE даже для владельца таблицы.
- [x] В журнале — только имена изменённых полей (§26.6 логирует действия, а не
      полезную нагрузку); исключения — переход статуса и смена исполнителя.
- [x] История (`job_activities`, `audit_logs`) не имеет FK на `organizations`:
      переживает удаление организации и не блокирует его.
- [x] Значения статусов, приоритетов, оплаты и источников проходят реестры и в
      приложении, и в CHECK-констрейнтах: строка вроде `'; drop table jobs; --`
      отвергается, а не сохраняется (unit-тест).
- [x] `assigned_user_id` проверяется по форме UUID и по составу участников.

## 4. Инъекции и разбор ввода

- [x] Все запросы идут через PostgREST-клиент (параметризация на его стороне).
- [x] Единственное место ручной сборки фильтра — поиск: значения экранируются
      (`%`, `_`, `\`) и берутся в кавычки (`quoteFilterValue`), длина терма
      ограничена. Покрыто тестами на запятую, кавычку, скобку и wildcard.
- [x] CSV-импорт разбирается чистым модулем без `eval`; каждая строка проходит
      ту же валидацию, что и форма, а затем ещё раз CHECK-констрейнты в БД.
- [x] CSV-экспорт обезвреживает ячейки, начинающиеся с `=`, `+`, `-`, `@`
      (formula injection при открытии файла в таблице).
- [x] `import_jobs` — `SECURITY DEFINER`, поэтому членство проверяется первой
      строкой функции; лимит 1000 строк за вызов; всё в одной транзакции.

## 5. Секреты и env (§33)

- [x] Секретов в репозитории нет; `.env*` в `.gitignore`.
- [x] Слоёная Zod-валидация env; сообщения об ошибках содержат только имена
      переменных, никогда значения.
- [x] CI работает на синтетических env-литералах — реальные ключи в CI не нужны.
- [x] Stripe-ключи пинятся к test-режиму, пока владелец явно не выставит
      `STRIPE_LIVE_MODE=live`.

## 6. Webhooks (§26.4)

- [x] Проверка подписи, уникальный id события, идемпотентность через
      `webhook_events`, ограниченное число попыток, raw body для Stripe.
- [x] Sanitized payload: в базу не попадает полное тело события.

## 7. Ошибки и утечки (§29)

- [x] Пользователю не показываются стектрейсы, тексты ошибок Postgres, имена
      исключений: `listJobs` бросает с кодом ошибки, а не с её текстом; экраны
      ошибок дают понятную фразу и кнопку повтора.
- [x] Страницы кабинета помечены `robots: { index: false }`.
- [x] `robots.txt` закрывает `/e/`, `/api/` и `/{locale}/app|onboarding|admin`:
      мета-тег читают после загрузки страницы — на один запрос позже, чем нужно
      для копии сметы, которую находят только по токену.
- [x] Тело `<script type="application/ld+json">` на публичной странице
      экранирует `<`: это единственный путь инъекции на странице, где всё
      остальное React печатает текстовыми узлами, а содержимое набирает владелец.

## 8. Приватность (§17.9)

- [x] Consent на SMS — только явный опт-ин; CHECK не даёт сохранить
      `sms_consent = true` без источника и отметки времени.
- [x] CSV-импорт **не** импортирует consent ни при каких колонках: согласие,
      перенесённое из чужой таблицы, — не согласие.
- [x] Аналитика передаёт id, коды и счётчики; имён, телефонов и адресов не несёт.
