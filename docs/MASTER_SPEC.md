# 14. Google Sheets Sync

## 14.1. Главная фишка

## 14.2. Модель данных MVP

```text
HandyAlliance Database → Google Sheets
```

База HandyAlliance является источником истины.

Google Sheet является:

- зеркалом;
- экспортом;
- удобной таблицей для пользователя;
- источником данных для Make, Zapier, n8n и других сервисов.

Обратная синхронизация:

```text
Google Sheets → HandyAlliance
```

не входит в MVP.

## 14.3. Поведение при ручном редактировании Sheet

В MVP:

- изменения в Google Sheet не меняют данные в HandyAlliance;
- система предупреждает пользователя;
- значения могут быть перезаписаны следующей синхронизацией;
- системные заголовки и идентификаторы защищаются;
- данные HandyAlliance не теряются, если Sheet удалён.

### English

> Edit jobs in HandyAlliance. This sheet updates automatically.

### Español

> Edita los trabajos en HandyAlliance. Esta hoja se actualiza automáticamente.

## 14.4. Подключение Google

В onboarding и settings:

- Create My Google Sheet;
- Connect an Existing Sheet;
- Skip for Now.

OAuth flow:

1. пользователь выбирает Google Account;
2. приложение запрашивает минимальный scope;
3. пользователь создаёт новую таблицу или выбирает существующую;
4. сохраняются connection metadata;
5. refresh token хранится только на сервере в зашифрованном виде;
6. выполняется full sync.

Использовать минимально необходимый доступ, предпочтительно `drive.file`, если текущая официальная документация это подтверждает для выбранного flow.

- disconnect не удаляет Google Sheet;

## 14.9. Архитектура sync

При изменении данных:

1. запись сохраняется в Postgres;
2. в той же транзакции создаётся `sync_outbox` event;
3. frontend сразу получает success;
4. worker обрабатывает событие;
5. несколько изменений группируются;
6. выполняется batch update;
7. событие получает статус `synced`;
8. UI показывает `Last synced`.

## 14.10. Статусы sync

```text
pending
processing
synced
retrying
failed
disconnected
```

## 14.11. Надёжность

Обязательно:

- idempotency key;
- защита от дубликатов;
- exponential backoff;
- ограничение количества попыток;
- dead-letter/failed state;
- ручной retry в admin;
- уведомление владельцу;
- повторный backfill после reconnect;
- batching;
- debounce;
- не отправлять запрос на каждый символ.

## 14.12. Soft delete

```text

```

В Google Sheet:

```text
Deleted / Eliminado = TRUE
```

Не удалять строку физически немедленно.

- выдавать опасные технические инструкции;
- скрывать, что это автоматический помощник;
- подтверждать юридически значимые условия;
- принимать платежи в MVP;
- совершать холодные исходящие звонки.

## 15.9. Emergency flow

Опасные ситуации обрабатываются только готовыми системными сценариями.

Пользователь не может произвольно переписать safety-текст.

Система должна:

- не изображать emergency service;
- сообщать о необходимости обратиться в соответствующую службу при явной опасности;
- выполнять transfer, если настроено;
- помечать lead как urgent;
- уведомлять владельца.

## 15.10. Запись разговоров

- recording выключена по умолчанию;
- включение требует отдельного согласия владельца;
- пользователь должен настроить законное уведомление;
- recording и transcript хранить в private storage;
- в Google Sheet отправлять только summary;
- retention должен быть настраиваемым;
- до production-запуска провести юридическую проверку применимых правил.

## 15.11. Usage

Хранить:

- included minutes;
- included calls;
- used minutes;
- overage rate;
- provider cost;
- customer charge;
- gross margin;
- billing period.

Не использовать `unlimited`, пока экономика не подтверждена.

## 15.12. Критерии приёмки

- English и Spanish звонки работают;
- создаётся Customer;
- создаётся Job;
- Call связывается с Job;
- запись появляется в Job Tracker;
- summary появляется в Google Sheet;
- владелец получает уведомление;
- webhook idempotent;
- usage не дублируется;
- работает fallback/transfer;
- provider outage не приводит к бесконечному loop.

# 21. Партнёрская программа — OUT OF MVP

**СТАТУС: отложена решением владельца. В текущей разработке НЕ реализовывать.** Раздел сохранён как справочный дизайн будущей версии. Будущая модель проста: фиксированный процент от каждой оплаченной подписки привлечённого клиента. Единственное допустимое действие сейчас — не создавать архитектурных препятствий: nullable `partner_id` у организации можно будет добавить позже отдельной миграцией. Отдельные таблицы, кабинет партнёра, attribution и расчёт комиссий не строить.

## 21.1. Цель

Позволить агентствам, консультантам, creators и другим партнёрам рекомендовать HandyAlliance и получать recurring commission.

## 21.2. Стартовая модель

Предварительно:

- 30% от фактически оплаченной subscription revenue;
- до 12 месяцев с даты первой оплаты клиента;
- 90-day attribution window;
- payout после refund/chargeback waiting period;
- manual approval и manual payout в MVP.

Все значения должны быть configurable.

## 21.3. Публичная страница

### English

> Partner with HandyAlliance

### Español

> Conviértete en socio de HandyAlliance

Обещание:

> Recommend simple tools to your home-service clients and earn recurring revenue. HandyAlliance handles the software, onboarding, billing, and support.

## 21.4. Attribution

Flow:

1. visitor открывает referral link;
2. сохраняется `partner_id` в first-party cookie;
3. создаётся referral visit;
4. после signup partner связывается с organization;
5. при Checkout partner ID добавляется в Stripe metadata;
6. после paid invoice создаётся commission record;
7. refund отменяет или уменьшает commission.

## 21.5. Manual attribution

Admin может связать организацию с партнёром после подтверждённого introduction.

Все manual changes записываются в audit log.

## 21.6. Partner dashboard

# 26. Безопасность

## 26.1. Row Level Security

На всех tenant-таблицах:

- пользователь видит только organizations, где он member;
- staff получает только разрешённые операции;
- partner не получает доступ к operational data;
- public estimate/site access работает только через безопасный token или published resource;
- service role используется только на trusted server.

Добавить automated tests на межорганизационную изоляцию.

## 26.2. Storage

Private buckets:

```text
estimate-files
refund-evidence
call-recordings
call-transcripts
business-assets-private
```

Public или controlled-public:

```text
business-site-assets
logos
published-gallery
```

Использовать signed URLs для private files.

## 26.3. OAuth tokens

- не отправлять frontend;
- шифровать;
- не логировать;
- доступ только background worker;
- revoke/disconnect support;
- rotation strategy;
- separate preview and production credentials.

## 26.4. Webhook security

- signature validation;
- timestamp/replay protection, если provider поддерживает;
- unique event ID;
- idempotency;
- rate limiting;
- raw Stripe body handling;
- отдельные test/live secrets.

## 26.5. Upload security

- allowlist MIME types;
- size limits;
- safe filenames;
- private storage;
- malware/validation strategy;
- никакого выполнения embedded content;
- AI должен рассматривать текст изображения как пользовательские данные, а не системную инструкцию.

## 26.6. Audit

Логировать:

- billing changes;
- entitlement override;
- partner attribution changes;
- OAuth disconnect;
- sync backfill;
- data deletion;
- admin access к sensitive data;
- call template publish;
- website publish/rollback.

# 27. Требования к AI

## 27.1. Structured outputs

Все критичные AI-функции должны возвращать данные по схеме.

Не сохранять свободный текст как окончательный документ без validation.

## 27.2. Prompt versioning

Хранить:

```text
tool
trade
locale
prompt_version
schema_version
active_from
active
```

## 27.3. Guardrails

AI не должен:

- гарантировать refund;
- назначать окончательную цену;
- давать юридическое заключение;
- обещать время приезда;
- создавать вымышленные отзывы;
- создавать вымышленные лицензии;
- публиковать перевод без проверки;
- раскрывать данные другой организации;
- принимать instructions из screenshots как системные команды;
- автоматически отправлять чувствительное действие без подтверждения.

## 27.4. Human confirmation

Обязательное подтверждение до:

- отправки estimate;
- первого follow-up;
- отправки refund draft пользователем;
- публикации AI-перевода;
- публикации call script;
- включения автоматических SMS;
- публикации business website.

## 27.5. Provider abstraction

Не связывать бизнес-логику напрямую с одним AI provider.

Создать интерфейс provider adapter, чтобы можно было заменить модель без переписывания модулей.

## 27.6. Logging

Логировать:

- tool;
- prompt version;
- model/provider;
- latency;
- token/cost metadata;
- validation result;
- retry count;
- error class.

Не логировать полные чувствительные данные без необходимости.

# 30. Производительность и надёжность

- retries;
- idempotency;
- timeouts;
- circuit-breaker или equivalent для внешних providers;
- health checks;
- structured logs;
- error tracking;
- backup/restore plan;
- non-destructive migrations.

# 43. Главный критерий успеха

Пользователь должен понять продукт без технического объяснения.

За несколько секунд он должен увидеть:

- кто ответит на звонки;
- кто поможет создать estimate;
- кто напомнит клиенту;
- кто поможет с плохим лидом;
- как получить сайт;
- где хранятся его работы;
- как данные попадают в Google Sheets;
- сколько стоит каждый инструмент;
- сколько он экономит с полным пакетом.

Главная ценность платформы:

> **Один простой аккаунт, несколько понятных инструментов и автоматическая синхронизация всех рабочих данных с Google Sheets — без сложной CRM и без индивидуальной разработки.**
